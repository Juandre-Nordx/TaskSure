# Recurring tasks

## Using the feature

On **Assign a task**, choose **Repeat → Daily / Weekly / Monthly** and, optionally, **Repeat until**. The default is **Does not repeat**. The first assignment is created immediately; later assignments are generated by the Laravel scheduler. Web owners and scoped managers can use these controls. The rebuilt mobile app provides the same controls for managers.

An existing task can be converted using **Make this task recurring** on its details screen. Choose its first repeat date, frequency and optional end date. Conversion preserves the original task's status, deadline, attempts and evidence. A new instance starts Assigned / Not reviewed and needs its own proof. Completing one occurrence does not stop the series.

The web **Recurring tasks** page lists manageable series, dates, state and occurrence counts. Owners can manage company series; managers can manage series they created while their assignees remain in scope. Employees can see recurrence details on their own tasks but cannot create, edit, pause or resume schedules. Existing organisation and policy-acknowledgement guards also protect the new endpoints.

Use **Pause series / Resume series** on the task or overview. Pausing preserves existing assignments. Resuming catches up missed occurrences through the end date. Owners can edit future template details in **Store settings**; those edits never change already-created tasks. Changing a single task's deadline, assignee or cancellation state affects that occurrence only. Pause the series separately when future assignments should stop.

## Future dates on the calendar

Both web and the rebuilt Android interface display **Planned recurring** entries for every scheduled date in the calendar's current day/week/month view. A daily series with no end date continues when navigating to later months. Weekly and monthly series follow their existing frequency and month-end rules. Only dates at or after the template's next occurrence are projected.

Tap a planned entry to read its instructions, responsible person, area, SAST deadline and scheduled start. Planned entries cannot be dragged, completed or opened as an already-created task. When the scheduler creates that occurrence, its normal task entry replaces the preview. Reading or navigating the calendar does not create database tasks or send assignment alerts.

Pausing the series, reaching the inclusive end date or losing valid assignment permissions removes its ungenerated dates on the next calendar load/refresh. Existing assignments and their history stay visible. Existing cancelled, reassigned or rescheduled occurrences are never recreated as previews, even if their template cursor is moved backwards. Owners and web managers retain their permitted calendar scopes; the mobile calendar remains personal for both managers and employees. Web assignee/category/priority/search filters apply to future dates; completion/review/overdue filters apply to actual tasks.

Each request is limited to an inclusive range with a maximum 93-day difference. Calendar navigation fetches the next range, so there is no fixed series horizon and no need to pre-create years of tasks. Web accepts FullCalendar's exclusive `start`/`end` or inclusive `from`/`to`, defaulting to the current SAST month when neither is supplied. Responses use private/no-store caching.

The mobile calendar opts in with `include_recurring=1` and handles planned-entry IDs separately. Older installed APKs keep their numeric task-only calendar until rebuilt, avoiding links to nonexistent tasks. The calendar addition needs **no extra migration** beyond the recurrence migration below. Rebuild web assets through the normal Docker release and rebuild/sync Android using the existing instructions. The calendar update uses **versionCode 5 / versionName 1.4**, following the recurrence release's versionCode 4 / versionName 1.3.

## Dates and generation

- Business dates and deadline times use **Africa/Johannesburg (SAST)**; stored timestamps remain UTC.
- Daily advances one calendar day, weekly seven days, and monthly retains its chosen day, using month-end in shorter months. A day-31 series returns to day 31 after February.
- Editing instructions or other content preserves the monthly anchor. Explicitly changing the next date or frequency establishes a new anchor from that date.
- The end date is inclusive. Leaving it blank repeats until paused. An ended series needs its end date extended in Store settings before resuming.
- Future instances retain the original interval between scheduled start and deadline. An overnight assignment is generated when its scheduled start arrives, even on the day before its deadline. Otherwise an occurrence becomes eligible on its SAST due date.
- The engine catches up eligible dates, up to **366 per template per pass**. Further overdue dates are processed on subsequent scheduler passes. Review old templates' **Next date** before enabling a scheduler: an old cursor can create historical assignments and their normal alerts.
- Row locks and the unique template/date constraint prevent duplicate occurrences. Assignment alerts use the existing deduplication key and queue delivery.
- Generation stops when an assignee is inactive or the series creator no longer has permission to assign to that person, including deactivation, revoked manager scope or a company mismatch. The overview displays the reason. Restore valid permissions or have the owner create a replacement series; editing content alone does not change its creator.

## Controlled Railway release

No production deployment, migrations or Railway service changes were performed for this feature.

1. Back up the existing PostgreSQL database and evidence volume. Review pending migrations with `php artisan migrate:status` in the running **web** service. Earlier pending completion/review or company-policy migrations have their own release requirements; follow those guides first.
2. Deploy only the approved source revision. The new migration is `2026_10_15_000001_add_recurring_task_options`: it adds nullable `ends_on` and `scheduled_offset_minutes` to `task_templates`. It does not convert/delete existing records. Existing templates keep their frequency, next date, deadline time and active state.
3. Keep **web → Settings → Deploy → Pre-Deploy Command** as:

   ```sh
   php artisan migrate --force
   ```

   Run it through the controlled deployment step after reviewing all pending migrations. Do not place migrations in the Docker image build, seed production or use reset/fresh/refresh commands. Preserve the existing APP_KEY, PostgreSQL service and private evidence volume. Confirm migration success and HTTP 200 from `/health` before starting the updated background services.
4. Deploy/restart the existing worker against the same approved revision after migrations. Configure the scheduler below. Use one scheduler replica. Verify one daily test series through its next occurrence, completion history and notification delivery before wider use.

### Add the missing scheduler service

Future recurring tasks require this service even when web and push delivery already work. The queue worker does not run the scheduler.

1. In the **existing Railway project/environment**, choose **New → GitHub Repo → Juandre-Nordx/TaskSure**, using the same approved branch/revision and root `Dockerfile` as web. Name this new service `scheduler`. Configure it before deploying. Do not create another database.
2. Copy/reference the existing web service's production variables, preserving the **same APP_KEY**, APP_URL and private PostgreSQL connection. Keep `APP_ENV=production`, `APP_DEBUG=false`, `CACHE_STORE=database`, `QUEUE_CONNECTION=database`, `SESSION_DRIVER=database` and `LOG_CHANNEL=stderr`. Keep the same reminder, email and mobile-push flags. Remove a conflicting DB_URL if the deployment uses separate DB_* fields. Secrets remain Railway variables.
3. Set **`PROCESS_ROLE=scheduler`** on this service. Leave web at `PROCESS_ROLE=web` and the queue worker at `PROCESS_ROLE=worker`. Leave custom build/start commands empty: the entrypoint selects **`php artisan schedule:work`**.
4. Keep **one replica**, an on-failure restart policy and service sleeping/serverless disabled. Leave its public domain, HTTP healthcheck and pre-deploy command empty. It needs no evidence volume. Deploy it after web's migrations succeed.
5. In scheduler logs, confirm `tasks:generate` and `tasks:remind` run each minute. In a Railway shell, the read-only command below lists their configured schedule:

   ```sh
   php artisan schedule:list
   ```

   Confirm a test template's next date advances and exactly one assignment appears for each eligible date. No current task is overwritten. A scheduler restart should preserve the database cursor and avoid duplicates.

If there is no queue worker, add another service the same way with **`PROCESS_ROLE=worker`**. Queued email/push needs that service and existing provider credentials. In-app alerts are stored by the task generator independently. Check `php artisan queue:failed` and worker logs for delivery errors. Real Android push receipt still needs a phone test.

For intentional diagnosis after reviewing due dates, `php artisan tasks:generate` runs the same generator once; it **writes eligible tasks and alerts**. Do not add it to a Docker build or run it merely to inspect configuration.

The backend accepts old clients that omit recurrence fields; their assignments remain one-off. The installed APK must be rebuilt to show the new controls.

In PowerShell from your existing TaskSure checkout, after getting the approved source:


Keep the existing `mobile/.env` API URL and `mobile/android/app/google-services.json`. Check the API is `https://tasksure-production.up.railway.app/api/mobile/v1` unless you intentionally changed the host. Do not replace existing Firebase or signing files with examples.

Raise versionCode further if a higher code is already installed/published. ## API additions

- `POST /api/mobile/v1/team/tasks` accepts optional `recurrence` (`daily`, `weekly`, `monthly`) and `recurrence_until` (`YYYY-MM-DD`, inclusive). Omit both for a one-off. The first deadline's date must be today or later in SAST when recurring.
- `POST /api/mobile/v1/tasks/{id}/recurrence` accepts `frequency`, `next_date` (today or later, strictly after the original deadline's SAST date), and optional `ends_on`. It links the existing task to a new series without changing its workflow. An already-linked task returns validation error 422.
- `POST /api/mobile/v1/recurring-tasks/{id}/status` accepts boolean `active`. The authenticated actor's current permissions determine access; client creator/company IDs have no authority.
- Task summaries/details include nullable `recurrence` with `id`, `frequency`, `active`, `next_date`, `ends_on`, `due_time` and `state`. Details include server-calculated `permissions.recurrence`. Existing auth, CSRF (web), validation and mandatory-policy rules remain in force.

See [validation](VALIDATION.md) for checks actually performed.
